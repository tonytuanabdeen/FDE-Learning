Testing & deployment are where trust is won or lost

Why these two phases carry the most risk — and the most value

Testing is how we earn the right to ship
  • An agent reasons its own path through subagents and actions — so "it worked when I tried it" proves very little.
  • Actions write real CRM data. A wrong tool call is a data incident, not a UI bug.
  • Customers see the output directly. One hallucinated policy can end up on social media.
Deployment is how we stay repeatable
  • An agent is a bundle of linked metadata plus Apex, flows, prompt templates, permissions and data.
  • Missing one dependency fails the deploy — or worse, deploys an agent that silently can't act.
  • Versions, activation and rollback must be scripted so any FDE can repeat them at 2am.

Our team rule: No agent reaches a customer-facing channel without a passing test suite and a deployment that was rehearsed in a full sandbox.

Testing goals and expectations

Test observable behaviour and outcomes, not identical generated sentences.

Prove the business outcome
Define what the user must achieve and what acceptable behaviour looks like.
Inspect the decision path
Verify topic and action selection, grounding and the resulting response.
Challenge boundaries and recovery
Cover permissions, ambiguity, edge cases, refusal, escalation and dependency failure.
Use the intended context
Test the representative persona, runtime identity, data state and channel.
Make evidence executable
Treat scenarios and expected outcomes as a repeatable, understandable design specification.

Traditional testing doesn't work for
non-deterministic agents

Design & Build Testing Deploy & Regression
TRADITIONAL SOFTWARE
Deterministic
  • Same input → same output
  • Test once, trust forever
  • End-of-cycle validation works
  • Stable regression baselines
AGENTIC AI
Non-Deterministic
  • Same input → variable outputs
  • Behavior drifts as models evolve
  • Late testing = late surprises
  • Requires continuous validation

AF Conversational Testing (ACT)

Agent API + evaluators Credits: yes SF rollback

Does the agent remember, and does it recover?

1
Multi-turn by design
Simulates a whole dialogue with a synthetic persona across many turns.
2
Asserts state, not just the last line
Context carry-over and memory — not only last-answer correctness.
3
Scriptable scenarios
Greet → give details → ask a follow-up → change your mind.
4
Conversational quality
Evaluate coherence and turns-to-resolution across the exchange.

When to use ACT vs. alternatives

Testing Center takes a Conversation History column — earlier turns go in, the next reply is checked (last turn must be the agent).
ACT simulates the whole multi-turn dialogue with a persona — frustrated customer, non-native speaker, distracted user.
Agent API harness when you need long/branching scripts, custom LLM-as-judge scoring, or load checks — drive the agent from Python. (Needs an External Client App, client-credentials flow.)
Demo cue: run “remember my name” with memory on (both turns pass), then off (turn 2 fails) — exactly what conversation testing is for.

UI & Channel testing w/ Playwright

Real Channel Credits: yes Data: may write

Testing Center checks the brain — Playwright checks what the customer sees

Why test the channel
  • Enhanced Chat on Experience Cloud / the React site
  • Real user journeys & multi-turn interactions
  • Rendered responses, rich content, handoff
  • Session & conversation continuity
  • Plugs into automated regression pipelines
Assert loosely on agent text, strictly on UI state.
journey.spec.tstest('full end-to-end concierge journey', async ({ page }) => {
    await page.goto(process.env.SITE_URL)
    await page.getByRole('button', { name: /chat/i }).click()
    const chat = page.frameLocator('iframe')
    await chat.getByRole('textbox').fill(
      'What sporting events are on in Riyadh?')
    // loose on wording
    await expect(chat.getByText(/Al-Noor Arena/i))
      .toBeVisible({ timeout: 30000 })
    // strict on UI
    await expect(page).toHaveScreenshot()
  })

Automated testing w/ Python & YAML

  Credits: yes Data: may write

Same idea as the CSV suite — but run by a process on every change

Tests as plain text, run by a script
  • A YAML file lists questions & expected results
  • A Python script sends each to the agent and prints PASS / FAIL
  • Assert on topic, action & key facts — not exact wording
  • Exit non-zero on failure; run locally, then in CI on every PR
Handle non-determinism & scale
  • Run each case N times, pass at a threshold (e.g. 4 of 5)
  • Tag cases: smoke (every PR) vs full (nightly)
