Suggested: Week 1

1

Get access to FDE GitHub

Do this first — approval can take days

Request access before anything else. Provisioning needs manager approval and can take 1 to 3 business days, so start it on day one while you set up your machine.

Request access through IdentityIQ Required

Raise the access request in the EIP Enterprise IGA Platform (IdentityIQ).

  1. Log into Salesforce Okta.
  2. Go to the EIP Enterprise IGA Platform: https://securityhub.internal.salesforce.com/iam/ignite/ignite-home
  3. Click Manage User Access, select Yourself, then click Next.
  4. Search for and select GHEC_forward-deployed-engineering-emu_Users.
  5. Click Next, add a Business Justification, then click Submit.
    • If a "Complete Work Item" window appears, select No for the "Do you have a case number for this request?" dropdown and click Proceed.
Careful: Provisioning requires manager approval and may take 1 to 3 business days. Request it early so it is not blocking you later.

What you'll set up — 5 steps · jump to the step-by-step detail below

1

Project folder structure

Learn where things go

A Salesforce DX project has a predictable layout. Learn where things go before you add to it.
Keep source code, tests, architecture decisions, scripts and project documentation discoverable. Do not commit credentials, tokens, customer secrets or production data.

The standard DX layout Required

customer-fde-project/

customer-fde-project/
├─ .claude/                    # Claude Code project config (CLAUDE.md, settings, skills)
│  ├── skills/                 # Project-specific Skills
│  ├── ├── architecture-review/
│  ├── ├── security-review/
├─ config/                     # Project-specific Context
│  ├── project-context.yaml    # Central configuration for the reusable architecture-review skill.
├─ docs/                       # ADRs, HANDOVER.md, design-diagrams, deployment-guides, test-results
│  ├── architecture/
│  ├── decisions/
│  └── deployment-guide/
│  └── tech-handover/
│  └── test-results/
├─ force-app/main/default/     # all Salesforce metadata (Apex, LWC, objects, flows)
│  ├─ classes/                 # Apex classes and tests
│  ├─ lwc/                     # Lightning Web Components
│  ├─ objects/                 # custom objects and fields
│  └─ flows/                   # flows
├─ manifest/                   # package.xml manifests for retrieve/deploy
├─ scripts/                    # apex / shell helper scripts
│   ├── setup/
│   └── validation/
├─ specs/                      # agent test specs, design notes
├── tests/
│   ├── apex/
│   └── playwright/
├─ .env
├─ .gitignore
├─ sfdx-project.json           # defines package directories and API version
└─ CLAUDE.md                   # acts as a persistent, project-specific instruction
└─ README.md
  • force-app/main/default is the source of truth for everything you deploy.
  • sfdx-project.json tells the CLI where your source lives. Do not delete it.
  • docs/ is where your handover and decisions live — treat it as a deliverable, not an afterthought.

Create a placeholder DX project

Scaffold, authorize, baseline

If you're not cloning an existing project, generate a fresh one to work in.

Generate the project Required

Generate

sf project generate --name customer-fde-project --template standard --manifest
cd customer-fde-project
git init
git branch -M main
git status

Use the generated Salesforce DX project as the starting point. Add the optional folders as your delivery needs emerge; avoid creating empty ceremony.

Verify it was created

sf project list ignored --help >/dev/null 2>&1 && echo "sf is working"
ls force-app/main/default
Authorize a sandbox with a clear alias Required

Use a client-env naming pattern. Sandboxes log in at test.salesforce.com.

Authorize

sf org login web --alias client-dev --instance-url https://test.salesforce.com --set-default
sf org list
sf org display --target-org client-dev
Careful: Never make production your default org. Production and Developer Edition use login.salesforce.com (the default host); sandboxes use test.salesforce.com.
Pull a baseline from the org Required

Bring the org's current metadata into your project so you start from a known state.

Baseline

sf project generate manifest --from-org client-dev --output-dir manifest
sf project retrieve start --manifest manifest/package.xml --target-org client-dev
git add . && git commit -m "baseline metadata from client-dev"
git push -u origin feature/short-description

Specific

# Retrieve a narrow, known metadata scope
sf project retrieve start --metadata "ApexClass:ExampleService" --target-org client-dev
Good pull request

Problem statement, approach, scope, screenshots/logs where useful, test evidence, deployment notes and rollback considerations.

Review discipline

Review security, permissions, bulk behaviour, error handling, test quality, maintainability and unintended metadata changes.

Optional — create a scratch org Recommended

Only if the project uses scratch orgs and you have a Dev Hub.

Scratch org

sf org login web --alias devhub --set-default-dev-hub
sf org create scratch --definition-file config/project-scratch-def.json --alias scratch1 --duration-days 7 --set-default
Validate a deployment (no changes yet) Required

A dry run confirms your project and org connection work end to end.

Validate

sf project deploy validate --source-dir force-app --target-org client-dev --test-level RunLocalTests

Before your first commit, make sure local state and secrets can never be checked in.

Add a safe .gitignore Required

# Secrets and sessions

# Node and test output

# IDE

Careful: sf org display --verbose prints a secret auth URL. Do not paste its output into chat, tickets, or Claude prompts. If you ever paste a credential by accident, rotate it and tell your lead.
4

Claude Code best practices

use it as an engineering partner

Claude Code can accelerate repository exploration, implementation, refactoring and test creation. It does not own engineering accountability. Treat generated changes as proposals that must be inspected, tested and reviewed.

Give context first

Explain the business outcome, repository structure, platform constraints, relevant files and acceptance criteria.

Plan before edit

Ask for repository reconnaissance and a proposed plan before authorising broad changes.

Work in small slices

Implement one vertical slice, inspect the diff, run tests and iterate. Avoid giant one-shot prompts.

Protect the boundary

Never paste secrets or restricted customer data. Review tool permissions and commands before approval.

Reusable prompt pattern:

Act as a senior Salesforce Forward Deployed Engineer working in this repository.

Outcome:
[Describe the customer/business outcome.]

Context:
[Relevant architecture, metadata, constraints and existing patterns.]

Task:
[One bounded engineering task.]

Acceptance criteria:
- [Observable behaviour]
- [Tests and quality gates]
- [Security and permission expectations]

Constraints:
- Follow existing project conventions.
- Do not invent metadata, APIs or business rules.
- Do not expose secrets or modify unrelated files.
- Ask before destructive actions or broad refactors.

First inspect the repository and propose a plan.
Do not edit files until I approve the plan.
After implementation, summarise changed files, tests run,
risks, assumptions and recommended next steps.

Claude Code is most useful when the project tells it how you work. Set these up once per project.

Write a project CLAUDE.md Required

Claude reads this at the start of every session. Keep it under ~100 lines: context, commands, conventions, and hard rules. Update it whenever you correct Claude twice about the same thing.

CLAUDE.md

# Salesforce AI Engineering Workspace
You are the Lead Salesforce Technical Architect and an Agentforce Forward Deployed Engineer. 

# Project: Salesforce Agentforce implementation 

**Documentation-first repo**: prompt Markdown files in `docs/architecture/prompts/` are the source-of-truth *specs*; the metadata under `force-app/` is their *output*.

## Context
- Goal: Build secure, maintainable, well-tested Salesforce solutions using Claude Code as an engineering assistant.

## Source of Truth
- Deployable Salesforce metadata lives in force-app/main/default/.
- Salesforce CLI manages org retrieval, deployment and validation.
- Git is the source of truth for version-controlled changes.
- Architecture decisions live in docs/decisions/.
- Harness policies and scripts live in harness/.

## Required Workflow
1. Inspect Git status and relevant existing metadata.
2. Understand dependencies and existing architectural patterns.
3. Present an implementation plan for non-trivial changes.
4. Implement the smallest coherent change.
5. Update or create relevant tests and documentation.
6. Run applicable deterministic validation.
7. Review the full diff for correctness, security and scope.
8. Report actual results and outstanding risks.

## Agentforce Standards
- Version regression scenarios and expected outcomes.
- Test happy paths, negative paths, edge cases and escalation paths.
- Separate deterministic assertions from LLM-based quality scoring.
- Do not claim tests passed without inspecting actual results.

## Skills to prefer

For work in this repo, the following skills are far more effective than generic reasoning — invoke them when relevant:

| Category | Skills | Primary Responsibilities |
| :--- | :--- | :--- |
| **Platform Development** | `sf-apex`, `sf-flow`, `sf-lwc`, `sf-soql` | Bulkified Apex, Flow triggers/subflows, reactive LWC bundles, selective queries. |
| **Developing Agentforce** | `sf-ai-agentscript` | editing the `.agent` file, previewing, publishing, debugging Agent Script behavior. | 
| **Quality** | `sf-testing`, `sf-debug` | >85% real coverage, bulk tests (200+ records), debug log parsing, heap/CPU limit analysis. |
| **Testing Agentforce** | `sf-ai-agentforce-testing` | writing/running `AiEvaluationDefinition` test specs (`sf agent test …`). |
| **Foundation** | `sf-metadata`, `sf-data`, `sf-docs`, `sf-permissions` | Source-format XML generation, bulk data export/import, permission sets/field security, docs retrieval. |
| **Integration** | `sf-connected-apps`, `sf-integration` | External Client Apps (ECA), Named Credentials, REST/SOAP callouts, Platform Events, CDC. |
| **Planning & Estimation** | `sf-flex-estimator` | Data Cloud and Agentforce Flex Credit sizing, consumption models, and SKU calculations. |
| **Data Cloud** | `sf-datacloud-*` | Ingestion, streaming transforms, DMO/DSO mapping, Identity Resolution, Segmentation, Activation. |
| **AI & Automation** | `sf-ai-*` | Agentforce topics, Agent Script syntax, utterance validation, session tracing, persona guardrails. |
| **Observing Agentforce** | `sf-ai-agentforce-observability` | investigating production sessions via STDM / Data Cloud traces. |
| **DevOps & Tooling** | `sf-deploy`, `sf-diagram-*` | `sf project deploy start`, delta builds, Mermaid architecture flows, visual diagrams. |

## Git and Delivery
- Work on a feature branch.
- Inspect the staged diff before preparing a commit.
- Never commit secrets or unrelated files.
- Never bypass required checks or human approvals.
- Do not deploy to production without explicit authorization.

## Commands
- Validate: sf project deploy validate --source-dir force-app --target-org client-dev --test-level RunLocalTests
- Apex tests: sf apex run test --target-org client-dev --test-level RunLocalTests --code-coverage --wait 30
- LWC tests: npm run test:unit

## Architecture Governance
- For architecture-related work, use the /architecture-review skill.
- Before making project-specific architecture recommendations, read "config/project-context.yaml".
- Use the official Salesforce Skills Library and relevant installed Salesforce development skills for implementation-specific guidance. Do not duplicate their instructions unnecessarily.
- Keep project-specific facts in the architecture context configuration rather than hard-coding them into reusable skills.
- Distinguish verified implementation details from documented intentions, assumptions, and proposed designs.
- Follow the repository's existing architecture documentation, ADR, testing, and deployment conventions.

## Rules
- Never commit secrets, auth URLs, or customer data. Use placeholders like CUSTOMER_1.
- Ask before deploying to any org or pushing to GitHub.
- Update docs/tech-handover/HANDOVER.md when architecture changes.
Daily habits Recommended
  • Plan first — for anything non-trivial, switch to plan mode (Shift+Tab). Claude explores the repo read-only and proposes a plan; you approve before any change.
  • Give it a way to check itself — point Claude at a validate command or the test suite so it can confirm its own work.
  • Read every diff — you are accountable for every line that ships. Small tasks, small commits.
  • Keep context clean — start a fresh session with /clear between unrelated tasks; run /compact when a session gets long. Put anything durable in CLAUDE.md, not the chat.
  • Point precisely — reference files with @path/to/file so Claude reads the right thing.
  • Fix the cause — if Claude gets something wrong twice, add a rule to CLAUDE.md or create a skill rather than correcting it again.
  • Protect data — never paste real customer data, credentials, or auth URLs. Use placeholders such as CUSTOMER_1.

/memory       edit CLAUDE.md files

Intermediate checkpoint:
Stage 03 · Technical leadership

Advanced — Lead delivery

Goal: make sound architecture decisions, engineer agentic solutions responsibly and guide a solution from discovery through production operations.

Suggested: Weeks 4–8+
Stage outcomeYou can lead a bounded customer workstream: discover the real problem, design an appropriate Salesforce architecture, implement and evaluate it, manage risks and explain production readiness.

1. Discovery and architecture

Discover the problem

Map personas, journeys, volumes, pain points, current systems, success measures and constraints.

Shape the solution

Compare native platform capabilities, custom code, integration and agentic approaches against the outcome.

Make decisions explicit

Capture assumptions, options, trade-offs, risks, dependencies and architecture decision records.

Design for operations

Include ownership, support model, observability, failure handling, rollback and change management.

2. Salesforce and Agentforce engineering

Choose the simplest architecture that satisfies the business need and platform constraints. Know where configuration is sufficient and where deterministic code, integration services or an agentic pattern is justified.

CapabilityEngineering considerations
Flow / Apex / LWCGovernor limits, bulkification, sharing, CRUD/FLS, transaction boundaries, error handling and testability.
Integration / APIsAuthentication, least privilege, retries, idempotency, timeouts, rate limits, schema evolution and observability.
Agentforce / AgentScriptAgent scope, topics/instructions, actions, deterministic boundaries, grounding, hand-offs, multi-turn state and safe failure modes.
Data 360 / RAGData access and consent, identity resolution, retrieval quality, freshness, chunking, relevance, provenance and data minimisation.
Custom UI / headlessAPI contract, session lifecycle, authentication, accessibility, latency, error states and secure client/server boundaries.

3. Testing, evaluation and quality engineering

Test more than the happy path. Use deterministic tests for deterministic logic, scenario suites for agent behaviour, and human review for ambiguous or high-impact outcomes. Treat evaluation datasets as maintained engineering assets.

Unit & integration

Apex tests, Flow tests where applicable, API contract tests, permission tests and data boundary checks.

Agent evaluation

Golden datasets, multi-turn scenarios, tool/action correctness, groundedness, refusal behaviour and regression tracking.

Browser E2E

Playwright for critical user journeys, accessibility and UI regression where browser automation is appropriate.

Human-in-the-loop

Review uncertain, sensitive or high-impact decisions and capture feedback for continuous improvement.

4. Security, responsible AI and production readiness

Security is part of design, not a final checklistApply least privilege, secure secrets handling, sharing and field-level security, input validation, safe output handling, auditability and data minimisation. For agentic systems, explicitly consider prompt injection, tool misuse, over-permissioned actions, data leakage and unsafe autonomy.

5. Technical leadership and customer delivery

Capstone lab · A production-minded agentic feature

  1. Choose a bounded customer scenario and define the user/business outcome.
  2. Document current state, target journey, architecture and non-functional requirements.
  3. Implement a thin vertical slice in a non-production environment.
  4. Create deterministic tests and an agent evaluation set, including failure and safety cases.
  5. Demonstrate observability, escalation and rollback behaviour.
  6. Present a go/no-go recommendation with evidence, residual risks and next steps.

Evidence: architecture artefacts, PRs, automated test/evaluation results, threat model and operational runbook.

Advanced checkpoint:
Finish line · Graduation

Ready for the field

Advanced sign-off
