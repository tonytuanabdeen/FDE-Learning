The agent development lifecycle

Salesforce Architects describe five phases; Salesforce's 2026 "Applied AI" paper adds a sixth, control and orchestrate, for multi-agent systems. Today we zoom in on the two orange and blue phases.

Click each phase. Key message: unlike SDLC, the ADLC doesn't end at release. Deployment is day one. Monitoring output becomes the next round of test cases.

Ask the room: which phase do you think causes most production incidents? Answer usually: test and deploy, because that's where assumptions meet reality.

Testing and deployment are where trust is won or lost

Testing is how we earn the right to ship

  • An agent reasons its own path through subagents and actions, so "it worked when I tried it" proves very little.
  • Actions write real CRM data. A wrong tool call is a data incident, not a UI bug.
  • Customers see the output directly. One hallucinated policy can end up on social media.

Deployment is how we stay repeatable

  • An agent is a bundle of linked metadata plus Apex, flows, prompt templates, permissions and data.
  • Missing one dependency fails the deploy, or worse, deploys an agent that silently can't act.
  • Versions, activation and rollback must be scripted so any FDE can repeat them at 2am.

Our team rule: no agent reaches a customer-facing channel without a passing test suite and a deployment that was rehearsed in a full sandbox.

Share a real (anonymised) story from a past engagement where a missing test or missing metadata component caused a go-live delay.

Agentic testing

Theory first, then the practical steps, then the recordings.

Test the decision, not just the sentence

What we assert on

  • Routing: did the agent pick the right subagent (formerly called a topic)?
  • Action: did it call the right action with the right inputs?
  • Outcome: does the response mean the right thing? Scored semantically, not by string match.
  • Safety: did it stay in scope, protect data and refuse what it should?

How we design cases

  • For each subagent: 5 happy-path phrasings, 3 edge cases, 2 negative cases as a starting point.
  • Vary tone, length, typos and language on purpose.
  • Run each suite more than once. Track pass rate over runs, not a single green tick.
  • Keep deterministic logic out of the LLM where you can, then test that logic with normal unit tests.

Point out the naming change: newer Salesforce docs call topics "subagents". The metadata type is still GenAiPlugin. New FDEs will see both terms in customer orgs.

Seven layers of agent testing

Walk the layers bottom to top: cheap and deterministic first, expensive and realistic last. Each following slide expands one layer.

Unit testing: make the tools trustworthy first

Every agent action is backed by something deterministic: an invocable Apex method, a flow, a prompt template or an API. If the tool is wrong, no amount of reasoning fixes it.

  • Apex actions: standard Apex tests with real assertions, including bulk and permission cases.
  • Flow actions: flow tests, plus Apex tests for autolaunched flows.
  • Prompt templates: preview with real records in Prompt Builder; batch-evaluate templates in Testing Center.
  • Run as the agent user: use System.runAs so you test with the agent's real permissions.

The most common silent failure we see: the action works for the admin but the agent user lacks field access. Testing with runAs catches it early.

Functional testing with Agent Builder preview

  • Simulation mode isolates tests from org data. Use it while instructions are still changing.
  • Live mode runs real actions against sandbox data. Use it before you commit a version.
  • Read the reasoning trace every time: subagent selected, action inputs, action outputs, final response.
  • From the IDE: sf agent preview --api-name Service_Agent, add --use-live-actions for live mode.

Preview is exploratory testing. It finds problems; it doesn't prove their absence. Anything you find here becomes a batch test case.

Play the recording, about 90 seconds. Pause on the trace view and point out where the action inputs appear.

Batch testing with Agentforce Testing Center

  • Lives as a tab in Agentforce Studio, next to the builder and observability. The older Setup version is now marked legacy.
  • Create test cases three ways: AI-generated from subagents and actions, Q&A tests from knowledge, or your own uploaded scenarios.
  • Each case states expected subagent, expected actions and expected outcome.
  • Scorers cover response accuracy, completeness, coherence, conciseness, latency and instruction adherence. You can add custom evaluations.
  • Conversation-level tests simulate a whole multi-turn dialogue with a synthetic persona.
  • Run history lets you compare quality across versions.

Runs consume requests and credits and can modify CRM data. Run Testing Center in sandboxes only.

Emphasise that AI-generated cases are a starting point. FDEs must review them; generated cases tend to be polite and well-formed, unlike real customers.

Tests as code: YAML specs and the Salesforce CLI

The test spec becomes AiEvaluationDefinition metadata, so tests are versioned and deployed alongside the agent. --result-format supports human, json, junit and tap.

Live-type the run command if time allows. Show the JUnit output, since that's what CI dashboards read.

Custom harnesses in Python with the Agent API

When Testing Center isn't enough, call the agent directly through the Agent API.

  • Long or branching multi-turn scripts
  • Custom scoring, including an LLM-as-judge rubric
  • Load and latency checks
  • A target for red-team tools such as promptfoo or PyRIT

Needs an External Client App with client credentials flow. Check endpoint shapes against the current Agent API guide before you reuse this.

Our team keeps a shared harness repo. Point new FDEs to it rather than having each one write their own.

UI and channel testing with Playwright

Testing Center checks the brain. Playwright checks what the customer actually sees in the channel.

  • Enhanced Chat on an Experience Cloud site or a website
  • Agent panels inside Lightning pages and LWCs
  • Handoff to a human, file upload, rich responses
  • Visual checks with screenshots; traces for debugging

Assert loosely on agent text (regex or keywords) and strictly on UI state.

Selectors inside the chat iframe vary by deployment. Show how to use the Playwright codegen tool to capture them.

Red teaming: try to make the agent misbehave

Select a card to see an example probe and the defence.

Tools and approaches

Salesforce native

Einstein Trust Layer (toxicity detection, audit trail), agent guardrail instructions, Testing Center custom evaluations for safety, permission-set reviews of the agent user.

Open-source scanners

promptfoo red-team plugins (OWASP LLM presets), Microsoft PyRIT, NVIDIA garak, DeepTeam, Giskard. Point them at the Agent API.

Human red team

A timed bug bash with personas: angry customer, social engineer, competitor, curious teenager. Use the OWASP Top 10 for LLM applications as the checklist.

Get written customer approval before running automated attack tools against their org, and run them only in sandboxes. Every successful attack becomes a regression test.

Automated and continuous testing

On every PRApex tests and a fast smoke suite
Quality gateAgent suite must pass the threshold, e.g. 90%
NightlyFull suite, conversation tests, red-team set
ProductionObservability, session traces, feedback
Back to testsEvery bad session becomes a new case
  • Start the gate as non-blocking for about two weeks; turn it blocking once the team trusts the numbers.
  • Schedule runs even without commits. Model, data and knowledge changes cause drift with no code change.
  • DevOps Testing Center can block an agent deployment until its suite passes, the same way failing Apex tests block a deploy.
  • Keep the pass-rate history; a slow decline is the signal, not one red run.

The deployment section will show the pipeline file that implements this gate.

The FDE testing playbook, in order

  1. Write success criteria and test scenarios during design, before building.
  2. Unit-test every Apex, flow and prompt template action as the agent user.
  3. Explore in Builder preview; turn every bug into a test case.
  4. Build a batch suite in Testing Center, then export it as YAML into Git.
  5. Add conversation and Playwright tests for the real channel.
  6. Red team with tools and people; add every hit to the suite.
  7. Gate deployments on the suite and schedule nightly runs.

Agentic deployment

An agent is metadata. Everything we know about Salesforce release management applies, with a few new steps.

An agent is a bundle of linked metadata

Metadata typeWhat it represents
AiAuthoringBundleThe draft agent as an Agent Script .agent file (new Agentforce Builder). Human-readable, easy to review in PRs.
Bot / BotVersionTop-level agent record and its versions. Only one version is active.
GenAiPlannerBundleThe reasoning engine config. Generated when a version is committed or published.
GenAiPlugin / GenAiFunctionSubagents (topics) and actions. In the new builder they can be local to one agent version.
GenAiPromptTemplatePrompt templates used by actions.
AiEvaluationDefinitionTesting Center test suites.
DependenciesApexClass, Flow, custom objects and fields, permission sets, Data Library and Data Cloud assets.

The new builder needs API v66.0 or later for the bundle types. API v68 introduces AiAgentDefinition and AiAgentDefinitionVersion. Always check the Agentforce DX "Move an agent" guide for the API version you target.

Key insight: draft lives in AiAuthoringBundle; runtime lives in Bot and GenAiPlannerBundle, created on commit. Committed versions are immutable.

package.xml: the manifest that says what moves

  • A manifest lists metadata types and members to retrieve or deploy.
  • Use exact member names as retrieved from the org; don't guess version suffixes.
  • Generate a starter manifest from an org with sf project generate manifest --from-org.
  • Use the Agent pseudo type to retrieve or deploy an agent and its parts in one go.
  • Keep one manifest per release and commit it with the change.

Show a manifest from a real (sanitised) project if you have one.

Salesforce CLI: retrieve, validate, deploy

Habits that save go-lives

  • Validate against production days before the release window, then quick-deploy the validated job.
  • Use --test-level RunLocalTests or RunSpecifiedTests for production.
  • Deploy dependencies before the agent.
  • Agents run as a user, and usernames differ by org. Use string replacements in sfdx-project.json.
  • After deploying, publish (or deploy the planner bundle) and activate the version.

Validate-then-quick-deploy is the single most useful habit for production releases; it separates test time from the change window.

Org browser: fetch metadata with clicks

  • The Salesforce Extension Pack for VS Code includes an Org Browser panel.
  • Browse types such as Bot, GenAiPlannerBundle or AiAuthoringBundle, then retrieve with one click.
  • Right-click a .agent file to publish it with the Agentforce DX command.
  • Great for discovery in a new customer org. For repeatable releases, move to a manifest.

Cursor and other VS Code forks can use the same extensions.

Org-based vs package-based development

Org-basedPackage-based (unlocked or 2GP)
Unit of releaseA set of changes described by a manifestA versioned, installable package
Source of truthThe org, or Git if you use CLI and DevOps CenterGit, always
Best forSingle-org customers, fast first releasesMulti-team or multi-org programmes, ISVs, reusable agents
RollbackRedeploy previous metadata, reactivate a previous agent versionInstall a previous package version
Watch out forOrg drift, missed dependenciesSetup effort, dependency design, metadata not yet packageable

Check the Metadata Coverage Report for packaging support of each agent type before you commit to a package-based design.

Most of our FDE engagements start org-based. Recommend packages when the customer runs multiple orgs or wants a reusable agent across business units.

Deployment options, from clicks to pipelines

Change sets

Salesforce's original point-and-click option between connected orgs.

  • Good for: tiny teams, one-off moves between sandbox and production.
  • Watch out: no version control, no rollback, manual component selection, limited support for newer agent metadata. Not recommended for agent work.

DevOps Center

Salesforce's free, Git-backed release tool with work items and pipeline stages, aimed at admins and mixed teams.

  • Good for: customers moving off change sets who want source control without building pipelines.
  • Watch out: fewer customisation hooks than a full CI/CD platform; confirm its current agent metadata support.

Salesforce CLI scripts

The commands from earlier, wrapped in a shell or Node script and run by a person.

  • Good for: FDE handoffs, first releases, rehearsals.
  • Watch out: depends on the person running it. Graduate to CI/CD once the script is stable.

CI/CD platforms

Jenkins, GitHub Actions, Azure DevOps, Bitbucket Pipelines and GitLab CI all run the same CLI commands headlessly with JWT auth.

  • Good for: engineering-led customers, gated agent test suites, full control.
  • Watch out: you own the pipeline, secrets and maintenance.

ISV DevOps tools

  • Copado: runs natively on Salesforce; user stories, pipelines, compliance.
  • Gearset: comparison-driven deploys, problem analysers, documented Agentforce metadata support.
  • AutoRABIT: CI/CD with strong security and compliance features for regulated industries.
  • Flosum: 100% native on the platform; popular where data residency matters.

Good for: large programmes, audit needs, mixed admin and developer teams. Watch out: licence cost and vendor-specific workflows.

We don't pick the tool; the customer usually has one. FDEs must be fluent enough in all of them to plug the agent into whatever exists.

PR openedAgent Script diff reviewed

The same shape works in Jenkins, Azure DevOps and Bitbucket Pipelines; only the YAML syntax changes. Secrets are placeholders here; never commit keys.

After the deploy: go-live steps people forget

  1. Confirm dependencies landed: objects, fields, Apex, flows, prompts, permission sets.
  2. Provision data: Data Cloud data kits, Data Library indexing, knowledge.
  3. Publish or commit the version, then activate it.
  4. Assign permissions to the agent user and end users.
  5. Connect channels: Enhanced Chat, Messaging, Slack, Lightning pages.
  1. Smoke test in the target org with preview and a small suite.
  2. Turn on monitoring: agent analytics, session tracing, Trust Layer audit.
  3. Rollback plan ready: reactivate the previous version, which stays intact because committed versions are immutable.

Data Cloud and Data Library assets often need their own deploy path (data kits). Plan for it early.

Common deployment gotchas

  • Manifest API version too low for the agent types.
  • Missing GenAiFunction or GenAiPlugin dependencies fail the planner bundle deploy.
  • Agent user username copied from the source org.
  • Trying to edit a committed version instead of creating a new one.
  • Scratch orgs that don't have Agentforce or Data Cloud provisioned; use sandboxes.
  • Testing in production because "it's only a read action".
