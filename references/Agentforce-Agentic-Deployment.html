The section promise

An agent is metadata — treat release as engineering, not a demo

Why deployment is where trust is kept or lost

1
A working demo is not a production system
Value is realised at release, not at build. The agent only earns trust once it ships — with every dependency — and keeps behaving.
2
Move the bundle, or it lands broken
Miss one dependency and the deploy fails — or worse, deploys an agent that silently can't act. The whole bundle moves together.
3
Immutable versions make rollback real
Committed versions are frozen. Rollback is reactivating a known-good version — not re-deploying and hoping.
4
The pipeline is the governance
A failing agent test blocks promotion exactly like a failing Apex test blocks a deploy. The gate protects the customer, not the calendar.
Take-home: everything you know about Salesforce release management still applies to agents — we're adding a few new metadata types and two new verbs: publish and activate.

2.1 · Draft → runtime → rollback

The draft is editable. The version is frozen.

Commit turns reviewable source into immutable runtime — that's what makes rollback reliable

AuthorAgent Script .agent
›
Commit / publishdraft → runtime
›
Version vNimmutable snapshot
›
Activateone version serves
›
Rollbackre-activate v(N-1)
The draft — AiAuthoringBundle
  • Human-readable Agent Script, diffable in a PR
  • Edited in the new Agentforce Builder or your IDE
  • This is what reviewers actually read
The runtime — AiAgentDefinition + AiAgentDefinitionVersion
  • Created on commit/publish from the draft
  • Committed versions are immutable — you can't edit them
  • Exactly one version is active & serving traffic
! Version note: the new builder needs API v66.0+. Metadata type names and behaviour evolve — always check the Agentforce DX "Move an agent" guide and the Metadata Coverage Report for your target API version before you script a release.

2.2 · Git, SFDX project & package.xml

Everything you click in Builder is text you can diff

One manifest per release, committed with the change

The three layers
  • SFDX project — sfdx-project.json + force-app/: how source lives on disk
  • package.xml — the manifest: which types & members move
  • The Agent pseudo-type — retrieve/deploy an agent and its parts in one go
Use exact member names as retrieved — don't guess suffixes. Generate a starter manifest from the org, then trim it to the release.
generate a starter manifest, then retrieve# starter manifest from an org
sf project generate manifest --from-org client-dev --output-dir manifest
# retrieve the whole agent in one go (Agent pseudo-type)
sf project retrieve start --metadata "Agent:Service_Agent" --target-org client-dev
package.xml — the NGA bundle (excerpt)<!-- draft -->
<types><members>Service_Agent</members><name>AiAuthoringBundle</name></types>
<!-- runtime: agent-level + versions -->
<types><members>Service_Agent</members><name>AiAgentDefinition</name></types>
<types><members>Service_Agent*</members><name>AiAgentDefinitionVersion</name></types>
<!-- dependencies travel with it -->
<types><members>GetOrderStatusAction</members><name>ApexClass</name></types>
<types><members>Service_Agent_Access</members><name>PermissionSet</name></types>
<types><members>Service_Agent_Tests</members><name>AiEvaluationDefinition</name></types>
<version>66.0</version>

2.2 · Discovery vs repeatability

Org Browser to discover · manifest to repeat

Two modes — know which one you're in

◰
VS Code / Cursor Org Browser
  • Browse AiAuthoringBundle, AiAgentDefinition, versions
  • Retrieve with one click — no manifest to write
  • Perfect for discovery in an unfamiliar org
  • Salesforce Extension Pack (works in Cursor too)
⛭
Manifest-driven release
  • One package.xml per release, in Git
  • Deterministic, reviewable, re-runnable
  • The unit the pipeline promotes
  • Graduate here the moment a release must repeat
Rule of thumb: click to learn the org; commit a manifest to ship from it. Discovery is interactive; release is deterministic.

2.3 · retrieve → validate → deploy

Validate days before · quick-deploy in the window

Nothing is committed until the quick-deploy — so the risky step is seconds, not minutes

the production release, in order# 1 · validate against prod days early — nothing is committed
sf project deploy validate --manifest manifest/package.xml \
  --target-org YOUR-ORG --test-level RunLocalTests

# 2 · quick-deploy the validated job inside the change window
sf project deploy quick --job-id 0AfXX00000000001 --target-org YOUR-ORG

# 3 · turn the draft into a version, then activate it
sf agent publish authoring-bundle --api-name Service_Agent --target-org YOUR-ORG
sf agent activate --api-name Service_Agent --version 2 --target-org YOUR-ORG
Habits that save go-lives
  • RunLocalTests for production deploys
  • Deploy dependencies before the agent
  • Agent runs as a user — usernames differ per org; use string replacements in sfdx-project.json, never hard-code
  • After deploy: publish the version, then activate
Same sf commands on macOS/Linux and Windows — only shell quoting differs (PowerShell uses a backtick for line continuation, not \).

2.4 · Org-based vs package-based

Start org-based · graduate to packages when it pays off

The unit of release is the real decision

Org-basedPackage-based (unlocked / 2GP)
Unit of releaseA set of changes in a manifestA versioned, installable package
Source of truthThe org (or Git via CLI / DevOps Center)Git, always
Best forSingle-org customers, fast first releasesMulti-team / multi-org programmes, ISVs, reusable agents
RollbackRedeploy previous metadata; reactivate prior versionInstall a previous package version
Watch out forOrg drift, missed dependenciesSetup effort, dependency design, not-yet-packageable metadata
FDE guidance: most engagements start org-based. Recommend packages when the customer runs multiple orgs or wants a reusable agent across business units — and check the Metadata Coverage Report for packaging support before committing to the design.

2.5 · From clicks to pipelines

The spectrum — clicks, scripts, pipelines

Same CLI underneath; the difference is who runs it and how it's governed

Change sets
Point-and-click between connected orgs. No version control, no rollback, weak for new agent metadata. Not for agent work.
DevOps Center
Free, Git-backed release tool — work items + pipeline stages. Good for admin/mixed teams off change sets. Confirm agent-metadata support.
CLI scripts
The commands wrapped in a shell/Node script, run by a person. Great for first releases & rehearsals; graduate once stable.
CI/CD platforms
GitHub Actions, Bitbucket, Azure DevOps, Jenkins, GitLab — same CLI, headless, JWT auth. You own pipeline, secrets, maintenance.
Data 360 kits
Knowledge & grounding are data, not metadata. Move Data Cloud assets via data kits + index the Data Library — a separate deploy path.
! Most-forgotten step: plan the Data 360 / Data Library path early. The agent can deploy perfectly and still answer from nothing because the grounding data never moved.

jobs:
  validate-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install --global @salesforce/cli
      - run: |                                   # JWT auth — secrets live in the store, never the repo
          sf org login jwt --client-id "${{ secrets.SF_CLIENT_ID }}" --jwt-key-file server.key \
            --username "${{ secrets.SF_CI_USER }}" --instance-url https://test.salesforce.com --alias ci
      - run: sf project deploy start --manifest manifest/package.xml --target-org ci --test-level RunLocalTests
      - run: |                                   # draft → version
          sf agent publish authoring-bundle --api-name Service_Agent --target-org ci
          sf agent activate --api-name Service_Agent --version "${{ vars.AGENT_VERSION }}" --target-org ci
      - run: sf agent test run --api-name Service_Agent_Tests --wait 20 --result-format junit --target-org ci  # THE GATE

2.6 · ISV DevOps tools

For large, governed, mixed admin/dev teams

No tool wins everywhere — match team shape, budget & cadence

Copado
Runs natively on Salesforce — user stories, pipelines, compliance tracking. Built for larger, governed teams.
Gearset
Comparison-driven deploys, problem analysers, documented Agentforce support. Fast to adopt, popular with mixed teams.
AutoRABIT
CI/CD with strong security & compliance features for regulated industries.
Flosum
100% native on-platform; popular where data residency matters.
Ask every vendor, before you commit: Do you support the agent metadata types today — show me a deployment. Can I run my own CLI test job as a pipeline step? Does a failing agent test block promotion? What's the audit trail and rollback story? This area moves fast — verify current support.

2.7 · Go-live & gotchas

The steps people forget — and the traps that bite

Deploy is step one of go-live, not the finish line

After the deploy — in order
Confirm deps landed Provision data (kits / Library) Publish version Activate Assign permissions Connect channels Smoke test Monitoring on Rollback plan ready
Rollback = reactivate the previous immutable version. Have the version number written down before you start.
Common gotchas
  • Manifest API version too low (<66.0)
  • Missing action/subagent dependencies fail the version build
  • Agent-user username copied from the source org
  • Trying to edit a committed (immutable) version
  • Scratch orgs without Agentforce / Data Cloud provisioned — use sandboxes
  • "It's only a read action" — tested in production

Open floor

Two things to take back — then your questions

Test the decision, not the sentence · treat the agent as metadata

Likely questions — crisp answers ready
  • How many test cases? Start 5 happy / 3 edge / 2 negative per subagent; grow from real failures.
  • Flaky results? Run each case N times, pass at a threshold (4/5); track the trend, not one run.
  • Blocking gate from day one? No — non-blocking ~2 weeks, then blocking once the team trusts the numbers.
  • Scratch orgs for agents? Usually no — use sandboxes; scratch often lacks Agentforce / Data Cloud.
  • Which ISV tool? None wins everywhere — match team shape, budget & cadence; verify agent-metadata support.
First-week homework
  • Build a small agent in your dev sandbox
  • Write 10 test cases, run them from the CLI
  • Retrieve it, write its package.xml, deploy to a 2nd sandbox
  • Run one promptfoo red-team scan against it
Then: rehearse validate → quick-deploy → publish → activate once, end to end, before any customer window.
